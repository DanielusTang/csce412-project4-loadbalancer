1. Overview

AggieForge Traffic Cloud is a C++ simulation of the load balancer that sits in front of a large company's web-server farm. Requests arrive from random source IP addresses, each one needing a random number of clock cycles of work, and the load balancer's job is to hand every request to a free web server as quickly as possible while keeping just enough servers switched on. The simulation is driven by a single integer clock: every tick the balancer admits any new arrivals, lets each web server make one cycle of progress, dispatches queued requests to servers that have gone idle, and then decides whether to grow or shrink the pool.

The system is balanced when the number of waiting requests stays between 50 × N and 80 × N, where N is the number of active web servers. Below the lower bound the farm is paying for idle capacity, so one server is removed; above the upper bound requests are waiting too long, so one server is added. After either change the balancer rests for n cycles before re-checking, which stops it from thrashing. Everything that defines a run (thresholds, task-time range, arrival rate, rest period, blocked IP ranges, logging mode) comes from a configuration file so that experiments never require a recompile.

Scope of this document. Per the project rules, the workflow and every class interface (inputs and outputs) below were designed before any code was written. Part 2 of the project builds exactly this design; the same AggieForge branding will appear on the Doxygen site, the log header and the demo video.

What the simulation must do

  • Take the number of web servers and the run time in clock cycles from the user; start with a full queue of servers × 100 requests.
  • Generate requests with a random requester IP, destination IP, processing time and job type ('P' processing or 'S' streaming), and keep injecting new ones at random times.
  • Run web servers that process one request for its full duration and then ask for the next one.
  • Autoscale the server pool with the 50×/80× rule and a cooldown of n cycles.
  • Block requests from configured IP ranges (firewall / DOS prevention) and count the rejections.
  • Write a colour-coded event stream in verbose mode and a START/END summary in both quiet and verbose mode, to the console and to a plain-text log file.
  • Bonus: a Switch that routes streaming jobs to one load balancer and processing jobs to another, each with its own statistics.

2. Data structures

Request — a struct

A request is plain data with no behaviour, so it is a struct: ipIn (requester IPv4 address as a string), ipOut (destination address), time (integer clock cycles of work), jobType ('P' or 'S') and arrivedCycle, the clock value when it was created. The last field is not in the assignment text; it is added so the balancer can report the average time a request waited in the queue in the end summary.

RequestQueue — a FIFO

The queue wraps std::queue<Request> and exposes only push, pop, front, empty, size and peakSize. First-in-first-out is the right policy because every request is equally important and the balancer must never starve an old request in favour of a new one. Wrapping the STL container (instead of using it directly) gives one place to record the peak queue depth and keeps the load balancer's code independent of the container choice.

3. Class diagram (UML)

The LoadBalancer is the hub. It owns its RequestQueue and its vector<WebServer> (composition — they live and die with the balancer), while it only references the IPBlocker, Logger and Config. That split is deliberate: the requirement that "multiple load balancers can be created" means two balancers must be able to share one firewall, one log file and one configuration while each keeps a private queue and server pool. WebServer holds at most one Request at a time; RequestQueue holds many. main.cpp creates and drives everything and is written by hand as required.

5. Workflow

Start-up (steps 1–4)

main loads config.txt, then prompts for the two interactive inputs the assignment requires — number of web servers and run time in cycles — which override the file. It constructs the Logger, loads every blocked_ranges entry into the IPBlocker, and builds the LoadBalancer (or, for the bonus, a Switch with one balancer for 'P' and one for 'S'). seedQueue(servers × 100) fills the starting queue, and the START summary records the server count, starting queue size, task-time range, thresholds, cooldown and blocked ranges so the log is self-describing.

The per-cycle loop (steps 5–10 = LoadBalancer::stepCycle)

  1. Arrival ARRIVE — with probability arrival_probability a new random request is created this cycle.
  2. Firewall BLOCK — IPBlocker.isBlocked(ipIn); a hit is counted as rejected and logged, and the request is discarded. Otherwise it joins the queue (bonus: the Switch picks the queue by job type).
  3. Servers tick DONE — every busy server advances one cycle; a server whose finishCycle_ is reached logs completion and becomes idle, i.e. asks for the next request.
  4. Dispatch ASSIGN — queued requests are popped FIFO onto idle servers until one side runs out. Wait time (cycle − arrivedCycle) is accumulated here.
  5. Autoscale SCALE± — only when the cooldown has expired: queue below 50×N removes one idle server, above 80×N adds one; either action sets cooldownUntil = cycle + n. Inside the band nothing happens.
  6. Heartbeat STATUS — in verbose mode a status line every status_every cycles (never every cycle, or a 100 000-cycle run would be unreadable); then the clock advances.

Ordering matters: servers tick before dispatch so a server that finishes this cycle picks up new work in the same cycle, and autoscaling runs after dispatch so it judges the queue that is genuinely still waiting.

Shutdown (step 9)

When cycle == runCycles the END summary is written in both modes: ending queue size, requests generated / processed / rejected, active servers and servers removed, scale-ups / downs, min and max servers, min and max queue depth, average wait and server utilization, plus the P/S split. This block is the "load balancer log" deliverable for the 20-server, 100 000-cycle quiet-mode run.

6. Design choices

  • Cooldown n after every scaling action. Adding a server does not shrink the queue instantly, and removing one does not grow it instantly. Without a rest period the balancer would add and remove servers on consecutive cycles (thrashing). n is configurable so experiments can show the trade-off between responsiveness and stability.
  • Hard min_servers / max_servers bounds. The 50×/80× rule alone could scale to zero servers when the queue empties, or without limit under a flood; bounds keep the simulation (and the "company") within a sane budget.
  • Never remove a busy server. Scale-down takes an idle server; if every server is busy the removal waits for the next check. No request is silently dropped by scaling — the only discarded requests are firewall rejections, and those are counted.
  • Configuration file, not constants. Every tunable (thresholds, task-time range, arrival probability, n, bounds, blocked ranges, mode, colour, log path, status interval, RNG seed) lives in config.txt, satisfying "configurable without editing code" and making the experiments in §8 a matter of editing one file.
  • Quiet vs verbose logging. Quiet prints only the START and END summaries — the deliverable log. Verbose adds the per-event stream and the periodic status line for the demo. The level is a constructor argument of Logger, so no if (verbose) clutter in the balancer.
  • Colour by event type. ARRIVE / ASSIGN green, DONE cyan, BLOCK red, SCALE+ / SCALE- yellow, STATUS magenta. Colours go to the console only; the file gets plain text.
  • Firewall at admission time. Blocking happens before a request ever touches the queue, so a DOS flood from a blocked range costs one comparison per request and never consumes server capacity. CIDR ranges are stored as (base, mask) integers so the check is a single bitwise AND.
  • Dependency injection for multiple balancers. LoadBalancer takes its Config, IPBlocker and Logger by reference and owns only its queue and servers. Two balancers therefore share the firewall and the log but keep separate statistics — exactly what the bonus Switch needs.
  • Request is a struct, queue is a FIFO wrapper. Plain data where there is no behaviour; a thin wrapper where the container choice should stay hidden and a peak-size counter is useful.

8. Planned experiments

Each run changes one parameter in config.txt and records ending queue size, the server count over time, rejections, average wait and utilization. The results become the capacity guide on the Doxygen main page and in the demo.
